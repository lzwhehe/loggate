# LogGate 调研：业界方案、真实痛点、差异点（2026-10-17）

调研由子 Agent 完成，来源见文末。

## 结论
方案 C 的核心思路是：每个目的地单独记录投递状态位，部分成功时只重投失败的目的地。这个方向是对的，但不是首创，Fluent Bit 已经按 output 分别重试。项目能立住，靠两件事：
1. **可验证**：用确定性的故障注入测试，证明丢失 0 条，并把重复率量化出来。
2. **安全场景特化**：
   - 带校验位的中国 PII 脱敏（身份证、手机号、银行卡），并标注 GB/T 43697-2024 的分级；
   - 安全日志归一化到 OCSF（或 ECS）。

**不拿来当卖点的**：吞吐量和插件数量。

## 1. 业界方案对比
| 系统 | 投递语义 | fan-out 部分失败时 | 缓冲 | 去重 |
|---|---|---|---|---|
| Vector | 端到端 ack，at-least-once | 回报最差状态，整条重发，健康 sink 会收到重复 | memory / disk（每 500ms fsync） | 无 |
| Fluent Bit | 按 output 重试，用尽后丢弃，或用 storage.keep.rejected 保留 | 各 output 独立 | memory / filesystem | 无 |
| Logstash | 持久化队列（PQ）at-least-once | 默认整条管道被阻塞，需要 output isolator | 内存 / PQ | DLQ 只收不可重试的错误 |
| Kafka Connect | offset，at-least-once | 一个 connector 对应一个目的地 | Kafka | 默认 errors.tolerance=none；KIP-610 之后才有 ErrantRecordReporter |
| OTel Collector | sending_queue + retry（默认 5 分钟后丢弃） | 实测：健康 exporter 吞吐下降，并产生约 0.2% 重复 | memory / file_storage | 无 |
| Filebeat | at-least-once | 只支持单一 output | memory / disk | add_id、fingerprint，下游 ES 覆盖写 |

## 2. 真实痛点
- 慢 sink 拖垮其他 sink（Vector #20496、OTel 实测、Logstash 官方文档）
- 重启后丢数据（Fluent Bit 只用内存时；Vector 的 fsync 窗口）
- 重试导致重复（OTel 约 0.2%；Filebeat 有专门的去重指南）
- 内存膨胀（Vector 按事件数计、不按字节数计）
- 磁盘写满
- 热加载：本次没有找到一手证据，写进 README 的 Limitations

## 3. 脱敏
- 方法：键级白名单 / 黑名单（fail-closed）、值级正则（Go 用 RE2，不支持 lookaround）、HMAC 哈希、令牌化、保格式脱敏
- 降低误报的关键是校验位：
  - 身份证：GB 11643 规定的 ISO 7064 MOD 11-2，加出生日期合法性校验
  - 银行卡：Luhn + BIN
  - 手机号：号段 + 11 位
- 性能：先做廉价的预过滤，再合并模式，并按字段级策略执行；用 testing.B 测吞吐和 allocs/op
- 合规：GB/T 43697-2024（2024-10-01 实施），分为核心、重要、一般三级

## 4. 差异点（诚实版）
1. 按目的地记录状态位，只重投失败的目的地，再加幂等键，达到 effectively-once。严格 exactly-once 需要下游支持幂等，这一点要写明。
2. 确定性故障注入测试，每个场景输出丢失数、重复数、恢复时间。这是最有说服力的部分。
3. 带校验的 PII 脱敏 + 分级标签，在合成数据上报告 P/R 和吞吐。
4. 归一化到 OCSF 的 2–3 个事件类（Authentication、Network Activity）。

## 5. 评测方法
- **基准**：
  - 吞吐：事件大小分 200B / 1KB / 4KB，分别测开启和关闭脱敏
  - 延迟：p50 / p99 / p999
  - 资源：CPU、RSS
  - 持续运行至少 30 分钟
- **故障注入场景**：
  1. 一个 sink 宕机 N 分钟
  2. 慢 sink（500ms）
  3. 负载下 kill -9 再重启
  4. 负载下插件注销或版本替换
  5. 磁盘写满
  6. 不可重试错误进入 DLQ
- **判定**：每条事件带序列号，在 sink 端对账，输出期望值与实收值的 diff
- **呈现**：公开硬件、配置、重复次数和原始数据，并给出置信区间

## 6. Go 依赖
- 日志主体：自己实现分段（segment）顺序追加，参考 nsq diskqueue
- 状态位：bbolt（简单）或 Pebble（写入快）
- 监控：prometheus/client_golang、grpc + health
- 配置：yaml.v3 + validator
- 限流和熔断：x/time/rate、sony/gobreaker
